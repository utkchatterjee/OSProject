# OSProject
Project background
SchedAI lets a user give a natural-language instruction (e.g. "Give process 4 more CPU time"), which an LLM controller running in userspace on the host converts into a constrained scheduling-policy update. A modified xv6 kernel validates and applies that update, changing how CPU time is distributed among processes. The LLM never runs inside the kernel — it only influences decisions the kernel enforces.
Scheduling algorithm: Weighted Round Robin. Each process gets a weight (bounded 1–5, default 1) that sets how many scheduling quanta it receives per pass through the run queue — weight 1 = one quantum, weight 3 = three quanta, and so on, with each quantum still subject to xv6's normal timer-driven yielding. Weight 1 for everyone reproduces plain round robin. A setweight(pid, weight) syscall changes a process's weight at runtime. Fallback behavior: if the LLM is unavailable, weights stay as they are; an invalid recommendation is rejected; a reset request restores weight 1.
Original four-day plan:
• Day 1 — Kernel awareness of weights: add a weight field to struct proc, initialize it to 1 for new processes, add a kernel function to change it, and wire up the setweight syscall (touching proc.h, proc.c, defs.h, sysproc.c, syscall.h, syscall.c, user.h, usys.pl). Deliverable: a syscall that changes a process's kernel-managed weight.
• Day 2 — Weighted scheduling: modify scheduler() in proc.c to actually implement weighted round robin, test with CPUS=1 and two or three processes at different weights. Deliverable: proof that changing a weight changes real CPU allocation.
• Day 3 — LLM integration: build controller/llm_controller.py and policy.py, which translate a natural-language instruction into JSON ({"pid", "weight", "reason"}), validate it (PID exists, weight in range, schema conformance), and forward the approved update to xv6. Fallback for communication is a manual command handoff; an automated QEMU serial connection is a stretch goal. Deliverable: a natural-language instruction changing a real kernel scheduling preference.
• Day 4 — Testing and presentation: build repeatable workloads (CPU-bound processes plus one simulating interactive behavior), compare baseline vs. AI-driven weight assignments, measure dispatch counts/CPU ticks and completion times, and prepare an architecture diagram, benchmark results, and a live demo.
The sections below are refinements to that plan, written for a 2–3 (possibly 4) day timeline, plus ways to work in OS file-handling concepts.
The plan is solid but slightly over-scoped for 2–3 days
The biggest risk isn't any individual step — it's that Day 3 (LLM integration) and Day 4 (testing) both depend on Day 1–2 going smoothly, and kernel debugging always eats more time than you budget. Here's how to compress and de-risk it, plus where file handling fits naturally rather than as a bolt-on.
If you only get 2–3 days: merge and cut, don't shrink everything proportionally
• Collapse Day 1 + Day 2 into one day. Writing the weight field, the syscall plumbing, and the weighted-RR scheduler logic are mechanically simple once you've read proc.c — the syscall boilerplate (syscall.h, syscall.c, usys.pl, user.h) is copy-paste-and-rename work, not design work. Budget a few focused hours for this, not a full day.
• De-risk the LLM step early, in parallel. Don't wait until Day 3 to touch the LLM controller. Write policy.py's validation logic and a hardcoded fallback mapping (a small dict of canned instructions → JSON) on Day 1 itself, while the kernel side is compiling/testing in the background. This gives a working end-to-end demo path even if the live LLM call is flaky or slow on demo day — fall back to "pre-scripted" translation and nobody can tell the difference in a live demo.
• Cut the QEMU serial automation stretch goal entirely if you're at 2–3 days. Manual copy-paste handoff (controller prints the setweight command, you type it into the QEMU console) is fine for a prototype and saves real time.
• Reduce to 2 test processes, not 3, for the comparison table. Two CPU-bound processes with weights 1 and 3 already demonstrates the effect clearly; the third "interactive" process is a nice-to-have for the writeup, not for the core proof.
Suggested compressed timeline (3 days)
1.  Day 1: Kernel weight field + syscall + weighted scheduler, tested with CPUS=1 and two dummy processes. In parallel, write policy.py validation + fallback JSON mapping.
2.  Day 2: Wire up the real LLM call (simple prompt → JSON schema), connect controller to kernel via manual handoff, run baseline vs. AI-instruction experiments, collect tick counts.
3.  Day 3: Polish — architecture diagram, benchmark table, short demo script, write-up. Buffer time for whatever broke on Day 1–2 (something will).
If a 4th day is available, that's buffer for the file-handling extension below, plus the "stretch" QEMU automation if things went smoothly.
Where file handling fits naturally (not as a tacked-on feature)
Rather than adding a separate file-handling subsystem, weave it into SchedAI itself — this makes it look like a deliberate design choice, not padding:
• A /proc-like stats file. Expose a pseudo-file (e.g. /procstats) that, when read, reports each process's PID, current weight, and quanta received so far. This is a genuine xv6 file-handling exercise (hook into xv6's file table / fileread path, or do something simpler like a special device file à la console), and it directly supports the Day 4 measurement goal — instead of hacking ad-hoc print statements, the benchmarking tool cats this file.
• A persistent decision log. Have the kernel (or the controller) write() every accepted/rejected scheduling update to a log file (/sched.log) with timestamp, PID, old weight, new weight, and reason string from the LLM's JSON. This is real file I/O, and it doubles as an audit trail for the presentation — cat sched.log during the demo shows the history of AI-driven decisions.
• A config file for policy bounds. Instead of hardcoding the weight range (1–5) in policy.py, read it from a small config file at startup. Minor, but it's a clean, low-effort way to touch "file handling as configuration" if one more checkbox is wanted without real risk.
Of these three, the stats file is the one to commit to if there's only room for one — it serves the existing Day 4 deliverable instead of competing with it for time. The log file is a close second since it's nearly free (a few write() calls at the point updates are already validated/applied) and makes the demo more compelling. Treat the config file as optional filler only if everything else finishes early.
One more small refinement: the fallback table already lists "LLM unavailable → retain weights" and "invalid recommendation → reject" — explicitly log both of those cases to the same log file. It's a nice detail for the write-up ("the system degrades gracefully and the log proves it") and costs nothing extra once the logging plumbing exists.
